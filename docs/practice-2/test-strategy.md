1. Цель тестирования
- Процессинговая цепочка проходит целиком
- Для каждого статуса карты и каждой причины отказа система выдает корректный ответ
2. Объект тестирования
- СМП:
  - Сервис авторизации: принимает решение одобрить или отклонить транзакцию по карте
  - Сервис управления картами: создание, хранение, поиск, обновление карт и резервирование денег на карте
  - Доменные объекты, с которыми мы работаем при тестировании: карта с её статусом и балансом, транзакция с результатом и причиной отказа, резервирование суммы
  - Вспомогательные элементы, которые используются при проверках: шлюз запросов, маршрутизатор транзакций, база данных карт
3. Уровни тестирования:
- модульное - проверки отдельных классов и функций, необходимы для быстрой точной локализации дефекта на ожидаемых сценариях.
- интеграционное - проверки взаимодействия нескольких компонентов друг с другом, необходимы для раннего обнаружения ошибок на стыках модулей.
- API - проверки внешних и внутренних интерфейсов запрос-ответ, необходимы для подтверждения соблюдения контрактов между сервисами.
- E2E - проверки системы целиком от входа до выхода, необходимы для подтверждения прохождения критичного бизнес-сценария всей цепочкой.

Общее правило для всех уровней: сначала проверяем позитивный сценарий, только потом негативные и отказы.
4. Область тестирования
- Что войдет
  - Сервис авторизации: 
    - полный цикл авторизации - от запроса на покупку до финального ответа APPROVED или DECLINED
    - проверка всех статусов карты при принятии решения - активная, неактивная, заблокированная, просроченная, удалённая
    - проверка всех причин отказа авторизации - карты нет, не тот статус, кончились деньги, превышен дневной или месячный лимит
    - корректность кодов ответа и текстов причин отказа
    - возврат денег при откате авторизации
  - Сервис управления картами:
    - работа с картами - создание, получение по номеру, поиск по фильтрам, обновление статуса или лимитов, мягкое удаление
    - резервирование денег на карте при успешной авторизации

- Что не войдет и почему:
  - Нагрузочное тестирование - не предусмотрено рамками практики 2, и требует дополнительной инфраструктуры
  - Тестирование безопасности (шифрование, PCI DSS, маскирование данных) - система учебная, эти механизмы не реализованы по заданию
  - Отказоустойчивость - сервис учебный, высокие нагрузки и продовая инфраструктура для обеспечения отказоустойчивости не предусмотрены
  - Тестирование брокера - низкий приоритет с риск-ориентированным подходом
  - Тестирование веб-интерфейса - вне рамок практики 2
  - PIN, CVV, 3-D Secure - используются заглушки, проверка не требуется
  - Реальные внешние платежные системы - их нет в проекте, система работает только со своими тестовыми картами

5. Риск-ориентированный подход

## Принципы приоритизации
По убыванию приоритета:
1. Сценарии отказа с финансовыми последствиями: превышение лимита, недостаток средств, повторное резервирование и т.п.
2. Проверки денежных значений - любые операции с деньгами: резервирования, возвраты при откате, покупки и т.д.
3. Проверки корректного отображения ответов и причин отказа пользователю/мерчанту
