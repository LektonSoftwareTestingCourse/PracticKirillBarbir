## 2. Бизнес-отказы

Проверены все ключевые бизнес-отказы. Проверяется не только код ответа, но и причина (`declineReason`).

| Исход | Код | Причина (`declineReason`) | Как воспроизводится |
|---|:---:|---|---|
| **Успешно** | `00` | `null` | Карта активна, денег достаточно |
| **Недостаточно средств** | `51` | `INSUFFICIENT_FUNDS` | Баланс меньше суммы покупки |
| **Превышен лимит** | `61` | `EXCEEDS_AMOUNT_LIMIT` | Сумма покупки больше дневного лимита |
| **Карта заблокирована** | `05` | `CARD_BLOCKED` | Статус карты переведен в `BLOCKED` |
| **Истек срок действия** | `54` | `CARD_EXPIRED` | Статус карты переведен в `EXPIRED` |
| **Карта не найдена** | `14` | `CARD_NOT_FOUND` | Запрос с несуществующим PAN |
| **Превышение частоты** | — | `RATE_LIMIT_EXCEEDED` | Более 100 запросов в секунду (код 429) |

## 3. Валидация входных данных

Проверены основные правила валидации шлюза (возвращается HTTP 400 и понятный текст ошибки):
1. **PAN**: неверная длина или буквы вместо цифр (`12345`, `400000ABC4567890`).
2. **Сумма (`amount`)**: нулевая (`0`) или отрицательная (`-500`).
3. **Обязательные поля**: отсутствие поля `pan`.
4. **Формат JSON**: синтаксически некорректный JSON.

## 4. Расхождения спецификации и кода

В ходе написания тестов найдены следующие несовпадения спецификации и кода сервисов:
1. **Статусы бизнес-отказов**: сервис авторизации внутри отдает HTTP 403, 404, 422, но Switch и Gateway переводят их в HTTP 200 с полем `status: "DECLINED"`, как требует спецификация.
2. **Лишние эндпоинты в сервисе карт**: методы получения списка (`GET /api/cards`), обновления (`PATCH`) и удаления (`DELETE`) карт реализованы в коде, хотя в спецификации их не было.
3. **Экспорт транзакций в CSV**: эндпоинт `GET /api/transactions/export` работает и доступен через Gateway, но не описан в `api-spec.md`.
4. **Валидация валюты**: Gateway проверяет только длину поля `currencyCode` (ровно 3 символа), из-за чего строка вида `"64A"` проходит валидатор.
5. **Идемпотентность логгера**: при повторной отправке транзакции сервис возвращает 200 OK при совпадении данных и 409 Conflict при несовпадении, хотя в спецификации описан только статус 201.

## 5. Доказательства работоспособности тестов

Чтобы доказать, что тесты действительно проверяют контракт и упадут при ошибке, в классе `IntentionalFailureVerificationTest` сделаны 4 проверки с `assertThrows(AssertionError.class)`:
1. Ожидание статуса 500 вместо 200 на `/health`.
2. Ожидание статуса `DECLINED` на успешной транзакции.
3. Ожидание 5-значного номера RRN вместо 12-значного.
4. Ожидание 200 OK при повторной отправке транзакции с измененной суммой (сервер возвращает 409 Conflict).
